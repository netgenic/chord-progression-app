# Обзор архитектуры

## Статус документа

Этот документ фиксирует целевую архитектурную форму проекта до начала production-разработки. Он описывает границы и направления зависимостей, но не выбирает преждевременно auth-провайдер, ORM, UI toolkit, audio engine или MIDI-библиотеку.

## Назначение системы

Chord Progression Library хранит, ищет, анализирует и воспроизводит аккордовые последовательности как абстрактные гармонические структуры. Каноническая прогрессия, например `i–VI–iv–V7`, является основной музыкальной сущностью. `Em–C–Am–B7` и `Cm–Ab–Fm–G7` — её представления в выбранных тональностях, а не отдельные записи прогрессии.

Пользователи являются сущностями первого класса в API и базе данных. Они могут создавать прогрессии, добавлять community-теги и сохранять избранное. При этом музыкальная идентичность прогрессии и пакет `packages/music-theory` полностью независимы от пользователей и механизма аутентификации.

## Контекст системы

Система состоит из следующих логических частей:

- web-клиент: каталог, поиск, редактор, воспроизведение и MIDI capture;
- API: HTTP-контракты, валидация, авторизация, orchestration и транзакционные операции;
- music-theory: чистая доменная библиотека музыкальных преобразований и анализа;
- database: PostgreSQL schema, migrations и persistence adapters;
- import pipeline: лицензируемые внешние датасеты, нормализация, canonicalization и provenance;
- browser capabilities: аудио и MIDI через изолированные адаптеры.

## Границы монорепозитория

Целевая структура:

```text
apps/web
apps/api
packages/music-theory
packages/database
packages/shared
packages/ui
scripts/importers
```

Допустимые направления зависимостей:

```text
apps/web ────────> packages/music-theory
      └──────────> packages/shared
      └──────────> packages/ui

apps/api ────────> packages/music-theory
      └──────────> packages/database
      └──────────> packages/shared

scripts/importers > packages/music-theory
                └> packages/database
                └> packages/shared
```

`packages/music-theory` не зависит от приложений, React, HTTP-framework, ORM, PostgreSQL, audio/MIDI APIs или пользовательской модели. `packages/shared` не должен становиться местом для случайной бизнес-логики; музыкальные правила всегда остаются в `packages/music-theory`.

## Основные потоки

### Просмотр и транспонирование

1. Клиент запрашивает канонические прогрессии и метаданные через API.
2. Выбранная пользователем тональность передаётся как параметр представления.
3. Абсолютные аккорды вычисляются общей music-theory библиотекой, а не дублирующей UI/API логикой.
4. Выбор тональности не создаёт новую запись прогрессии.

### Создание прогрессии

1. Пользователь вводит аккорды вручную либо через MIDI adapter.
2. Music-theory распознаёт аккорды, предлагает тональности и строит Roman Numerals.
3. При неоднозначности пользователь подтверждает тональность.
4. API валидирует команду, проверяет права и сохраняет каноническую прогрессию и пользовательскую связь.

### Импорт датасета

1. Dataset-specific parser создаёт нормализуемые записи с provenance.
2. Pipeline сегментирует, нормализует и canonicalizes последовательности через music-theory.
3. Дубликаты объединяются по версионированной канонической идентичности.
4. Каждое corpus occurrence сохраняет исходное происхождение и исходное представление.

## Общие инварианты

- Каноническая прогрессия не содержит выбранную для отображения тональность.
- Пользователь, auth identity, favorite и community tag не входят в музыкальную идентичность.
- Chord identity отделена от inversion и voicing.
- Любые внешние данные валидируются на границе системы.
- Авторизация выполняется сервером для каждой изменяющей операции.
- Импорт воспроизводим, идемпотентен и не теряет provenance.
- UI, API и importer переиспользуют одну реализацию музыкальных правил.
- Архитектурно значимое изменение оформляется ADR до или вместе с реализацией.

## Отложенные решения

До появления проверяемых требований не выбираются:

- email/password, OAuth или конкретный auth-провайдер;
- ORM и инструмент миграций;
- HTTP-framework и формат генерации API schema;
- frontend framework details, state manager и CSS/UI toolkit;
- audio engine, sampler и источник piano assets;
- MIDI helper library и точная browser fallback policy.

Решение каждой из этих тем потребует отдельного ADR.
